<objective>
Give HOOK-01 the durable half of its promise and ship HOOK-03's table: a persistent, opt-in
`hubspot_webhook_events` store that makes each HubSpot `eventId` a no-op after successful handling,
survives cache loss and worker restarts, recovers from a worker that dies mid-flight, and prunes on
a configured retention.

Purpose: 05-01 proved receipt end-to-end but its queued job has no memory. HubSpot retries on any
connection failure, timeout or 4xx/5xx, so redelivery is the normal case rather than the exception,
and a cache-backed dedupe cannot satisfy D-01. This plan is the layer everything after it stands on
— 05-03's typed events and handlers run *inside* the claim this plan opens.

Output: A false-by-default `webhooks.enabled` feature flag with its own migration group, the event
store port and its database implementation, claim → dispatch → complete wiring in the queued job, a
directed missing-table error, and the prune command.

**Design resolution carried into this plan (state it, do not re-litigate):** `REQUIREMENTS.md`
HOOK-01 still reads "Dedupe on `eventId`, cache driver by default". `05-CONTEXT.md` D-01 supersedes
it and `05-RESEARCH.md` records the supersession explicitly under *Deprecated/outdated*. The store
is database-backed. One table serves both roles — the mandatory claim lifecycle (D-01/D-03) and
HOOK-03's opt-in audit payload — because the audit trail and the idempotency key are the same row.
</objective>

  <name>Task 1: Decide the hubspot_webhook_events schema and claim model</name>
  <decision>The on-disk shape of `hubspot_webhook_events` and how a claim is recovered when a worker dies holding one.</decision>
  <context>
D-02 is rated one-way in `05-CONTEXT.md`: once a consumer sets `HUBSPOT_WEBHOOKS=true` and runs
`php artisan migrate`, this schema is in their database and every later change to it is a second
migration against rows the package itself wrote. `05-CONTEXT.md` leaves the exact schema, indexes
and retention default to the agent's discretion, so the choice below is genuinely open — the
feature flag is decided, the table shape is not.

`05-RESEARCH.md` Pitfall 3 names the failure this choice governs: a unique `eventId` alone
distinguishes no state, so a process death after claim and before completion turns the event into a
permanent no-op that nothing reports.
  </context>
  <options>
    <option id="option-a">
      <name>One table, lease-recovered claim (recommended)</name>
      <pros>One migration, one retention policy, one row per event. The audit trail and the
      idempotency key are the same record, so an operator inspecting the table sees why an event was
      skipped. A `claimed_at` older than `hubspot.webhooks.claim_lease` is re-claimable, so a dead
      worker costs a delay rather than a lost event.</pros>
      <cons>The lease window is a tuning value that can be wrong in both directions: too short and
      two workers can genuinely overlap on a slow handler, too long and recovery is slow.</cons>
    </option>
    <option id="option-b">
      <name>Two tables — a lock table and an audit table</name>
      <pros>The opt-in audit payload is physically separate from the mandatory dedupe key, so
      HOOK-03's "optional" reads literally at the schema level.</pros>
      <cons>Two migrations and two retention policies to keep in step, and the undo cost of the
      one-way door doubles. An operator now has to join two tables to answer one question.</cons>
    </option>
    <option id="option-c">
      <name>One table, status only, no lease</name>
      <pros>Simplest possible schema and no tuning value at all.</pros>
      <cons>Exactly `05-RESEARCH.md` Pitfall 3: a worker that dies after claiming strands the event
      permanently, and the retry sees a row and exits without checking completion state.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
</task>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-06 | Tampering | DatabaseWebhookEventStore | high | mitigate | `event_id` is an opaque string bound to a fixed column width and passed only through the query builder's parameter binding; it is never concatenated into SQL and never used as a file path or cache key prefix. |
| T-05-07 | Information Disclosure | hubspot_webhook_events payload column | high | mitigate | The payload column is nullable and written only when `hubspot.webhooks.audit_payload` is explicitly true; the default is false, and the raw request body, signature header and client secret are never persisted in any column. |
| T-05-08 | Denial of Service | Redelivery storm | medium | mitigate | The unique index on `event_id` means a redelivery updates rather than inserts, and `hubspot:webhooks:prune` bounds the table against `hubspot.webhooks.retention_days`. |
| T-05-09 | Repudiation | Stranded claim | high | mitigate | A claim older than `hubspot.webhooks.claim_lease` is re-claimable with an incremented attempt counter, so a worker killed mid-handling cannot silently convert an event into a permanent no-op; the lease-recovery path carries its own test. |
| T-05-10 | Elevation of Privilege | Migration activation | medium | accept | Enabling webhooks adds a table to the consumer's database. Accepted because D-02 makes this an explicit, documented, false-by-default opt-in, the migration is published unconditionally so a team may own the file, and no code path flips the flag on the consumer's behalf. |
| T-05-11 | Denial of Service | Unbounded event_id length | medium | mitigate | A `NormalizedWebhookEvent` whose `eventId` exceeds the column width is rejected at normalization with the package's own exception rather than truncated, because a truncated key would silently alias two distinct events onto one dedupe row. |
