<objective>
Complete HOOK-01's routing surface: typed Laravel events for the core semantic families, the
configured handler map including `'*'`, the dispatch order D-08 fixes, and the
`assertWebhookHandled` seam Phase 2 deliberately deferred to this phase.

Purpose: 05-01 delivers one generic event and 05-02 makes it durable. Neither gives a consumer a
way to say "when a contact's email changes, do this" without pattern-matching a subscription-type
string themselves. This plan is the public contract consumers write code against, which is why D-05
and D-07 are both rated costly in `05-CONTEXT.md`.

Output: Three family typed events plus the one registered specialization the ROADMAP names, a
package-owned handler interface, a validated container-resolved handler map, the fixed dispatch
order, and the inbound receipt log with its facade assertion.

**Design resolution carried into this plan (state it, do not re-litigate):** D-09 fixes the initial
typed surface at three core semantic families — property changes, lifecycle, associations —
and `05-CONTEXT.md` defers further dedicated classes as additive future work. ROADMAP success
criterion 4 names `ContactPropertyChanged` by name. Both are satisfied by a most-specific-first
resolution over a closed table: `contact.propertyChange` resolves `ContactPropertyChanged`, every
other `*.propertyChange` resolves the `ObjectPropertyChanged` family class, and exactly one typed
event is ever emitted per item. Adding a second specialization later is a new row in that table and
a new final class, which is additive and semver-safe.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Normalized event -> application handler code | The package invokes application classes named in config, driven by attacker-influenced routing input. |
| Payload subscription type -> class resolution | An untrusted string selects which package class is constructed. |
| Handler exception -> application logs | A handler's own failure text may carry payload content. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-12 | Elevation of Privilege | HandlerMap | high | mitigate | Handler classes come only from `hubspot.webhooks.handlers`, never from the payload; every entry is proved to exist and to implement `Webhooks\Contracts\WebhookHandler` before any handler runs, and a failure raises `ConfigurationException` rather than resolving whatever the container returns. |
| T-05-13 | Tampering | TypedEventMap | high | mitigate | The subscription-type to class table is closed and package-owned; no FQCN is constructed from payload text, and an unrecognized type resolves no class at all rather than a fallback the payload can steer. |
| T-05-14 | Denial of Service | Handler execution | medium | mitigate | Handlers run on the queue and never in the HTTP request, so a slow handler cannot hold the webhook route open; 05-02's claim lease bounds how long a stuck handler blocks a redelivery of the same event. |
| T-05-15 | Information Disclosure | Job failure path | medium | mitigate | The job re-throws a handler's exception unchanged and adds no payload-derived context of its own; the inbound receipt log is in-memory, test-only, and never written to a log or a database column. |
| T-05-16 | Repudiation | Receipt recording | medium | mitigate | A receipt is recorded only after `complete()` returns, so an assertion can never report as handled an item whose handler threw. |
</threat_model>
