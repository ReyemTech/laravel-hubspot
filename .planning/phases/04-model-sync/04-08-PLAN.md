`04-RESEARCH.md` Open Question 1 found a genuine gap: D-06's named trait surface has no
collection-level method, and neither the design spec nor `04-CONTEXT.md` named one, while success
criterion 4 cannot be demonstrated without an entry point. D-16 closed it after research, and the
argument was: it mirrors the trait's own static convention (`whereHubspotId`, `syncedToHubspot`,
`pendingHubspotSync`), and because the bound object type follows from the model class it needs no
grouping guard — which a facade form would have needed, since a facade cannot assume one object type
for a mixed collection. Typed `iterable` so an Eloquent Collection passes without `->all()`.

One implementation detail the owner should see before confirming: "needs no grouping guard" means the
object type is not inferred from the collection's contents. It does **not** mean a mixed collection is
accepted. The next task asserts every item is an instance of the called class and throws otherwise,
which is this package's throw-rather-than-guess rule applied to a mixed collection — the alternative is
writing one model's rows into another model's object type.

This is a method on a trait consumers apply, in the same class of change as D-06. Renaming it after
release is a breaking change.

  <action>
**`SyncsToHubspot::syncManyToHubspot(iterable $models): void`.** A static, mirroring the trait's own
static scopes and Laravel's `SoftDeletes`/`Prunable` shape D-05 benchmarks against. It asserts every
item is an instance of `static::class` and throws naming both classes otherwise — the object type is
not inferred from the collection's contents, so a foreign instance would otherwise write one model's
rows into another model's object type. It consults `SyncGate` and then dispatches exactly one
`SyncHubspotObjectsBatchJob` through the injected `Illuminate\Contracts\Bus\Dispatcher`. `iterable` is
the parameter type so an Eloquent Collection passes without `->all()`; materialise it once inside
rather than iterating a generator twice.

**`Sync\SyncHubspotObjectsBatchJob`.** Same primitives as the single job — `ShouldQueue`, `Queueable`,
`InteractsWithQueue`, `SerializesModels`, `Batchable`, `deleteWhenMissingModels = true` — and the same
`SyncGate` re-check in `handle()`. It resolves the map for every model on the worker (D-09), partitions
eligible records by their persisted link, calls `ObjectGatewayContract::updateMany()` once for linked
records, and calls `ObjectGatewayContract::upsertMany($objectType, $idProperty, $records)` once for
unlinked records. Each non-empty identity group is chunked to at most 100 inputs, so the request count
is `ceil(update_count / 100) + ceil(upsert_count / 100)`. Write no new HTTP code.

**It skips trashed models exactly as the single job does.** 04-06 gave `SyncHubspotObjectJob` an
early return when the re-fetched model is `trashed()`, because `SerializesModels` restores soft-deleted
models and the delete path owns an archived record's state. The batch job faces the same race with more
surface: `SerializesModels` re-fetches the whole collection on the worker, so any model soft-deleted
between dispatch and handling arrives with `trashed() === true`. Filter those out of the records array
*before* assembling it — not after the call — and log each skipped model the same way the single job
does. Without this, one member of a collection could push a stale property write to a record the delete
path has already archived, in a batch request the single-model path would have refused.

Take the returned records from `BatchResult::recordsDespitePartialFailure()`, not `records()`, and say
why in the docblock: `records()` returns nothing for a partial batch, so a 207 in which most records
landed would write no link rows at all and a retry would rediscover records already created. Choosing
the partial accessor is the caller stating that it accepts a partial batch, which is exactly what the
two-accessor design forces. Log `BatchResult::errors()` and do not throw — a partial batch is not a
failed job, and the models with no row are picked up by `pendingHubspotSync()`.

State in the class docblock, as the single job already does, that `Batchable` is present only for
interoperability with an application that wraps its own dispatches, that it is migration-free unless
`Bus::batch()` is called, and that **this package never calls it** — SYNC-03's bounded batch transport
uses HubSpot's own batch endpoint, and nothing here obliges a consumer to run a `job_batches` migration.

**`HubspotManager::assertSynced()`** widens its first parameter to `string|Model`. A bound model
resolves its object type through `ModelBindings`; an unbound one throws
`ConfigurationException::unboundSyncModel()` rather than guessing. Widening a parameter is caller-safe
and semver-safe on a `final` class (D-17 in `PROJECT.md`), and the method's own docblock already
records that Phase 4 does this — replace that forward-looking sentence with what is now true. Update
`Testing\HubspotFake` and `Testing\RequestLog` only as far as the resolution requires; the assertion's
subset and strict-comparison rules do not change.

This is the first reference from the package root namespace into `Sync`. Run the architecture suite
and `verify-arch-rules-fire.sh` before assuming it is permitted; if a rule objects, resolve the object
type through a container-bound contract rather than widening the rule.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied collection → one object type | The static's own class decides the object type; the collection's contents must not |
| HTTP 207 → local link rows | A partial batch decides which local rows are considered synced |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-33 | Tampering | a foreign instance in the collection | high | mitigate | Every item is asserted to be an instance of the called class and a mismatch throws naming both. Inferring the object type per item is the grouping guard D-16 chose the static form to avoid, and guessing it from the called class alone would write one model's rows into another's object type |
| T-04-34 | Denial of Service | N requests rather than bounded identity-aware batching | high | mitigate | Homogeneous groups assert `assertRequestCount(1)` over a collection large enough that an N-request implementation cannot coincidentally match; mixed state asserts at most one `updateMany` plus one `upsertMany` |
| T-04-35 | Information Disclosure | discarding a partial batch | medium | mitigate | `recordsDespitePartialFailure()` plus logged errors, so records that landed get link rows and a retry converges through upsert rather than rediscovering them |
| T-04-36 | Denial of Service | an unrequested `job_batches` migration in a consumer app | medium | mitigate | `Batchable` is present but `Bus::batch()` is never called; asserted by a repository-wide grep and by the absence of any such migration |
</threat_model>
