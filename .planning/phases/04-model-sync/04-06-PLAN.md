<objective>
Deletes cannot surprise anyone.

This plan builds the delete-policy table from design spec §7 on the three Eloquent events that
actually distinguish its rows, rather than on the one that does not. `deleted` fires identically for a
`SoftDeletes` model's ordinary `delete()` and for its `forceDelete()`; `trashed` fires if and only if
a genuine soft delete happened; `forceDeleted` fires only on a hard delete. Branching inside a
`deleted` handler on `$model->trashed()` misclassifies a hard delete, because the in-memory
`deleted_at` is already set by the time it runs.

Purpose: ROADMAP SC5's first four clauses, and the resolution of the update-racing-a-soft-delete item
`04-CONTEXT.md` flagged for the planner rather than deciding.
Output: a pure `DeletePolicy` resolver, an archive job, three correctly-selected event handlers, and a
`restored` handler that flags without ever nulling.
</objective>

  <name>Task 1: What does `hard_delete => 'warn'` do? — ANSWERED 2026-07-30</name>
  <resolution selected="warn-skips-loudly">
**The owner selected `warn-skips-loudly` before execution began.** `warn` takes the same action as
`guard` — the record is **not** archived — and logs at **warning** level rather than info. Locked as
**D-21** in `04-CONTEXT.md`; do not re-open this gate, and do not re-ask. Proceed directly to Task 2.

| value | action | log level |
|---|---|---|
| `guard` (default) | skip | info |
| `warn` | **skip** | **warning** |
| `allow` | archive in HubSpot | — |

The reasoning recorded with the decision: a config value whose plain-English reading (*"warn me
instead of doing it"*) is the opposite of its behaviour is a trap, and because HubSpot has no
unarchive endpoint the failure is silent until somebody reads the CRM.

Task 4's document amendments still apply and are now mandatory: design spec §7 and
`.planning/REQUIREMENTS.md` SYNC-04 must state what all three values do.
  </resolution>
  <decision>
`hard_delete` takes three values and only one of them is defined anywhere. Decide `warn`'s behaviour
before it becomes a config value consumers have written.
  </decision>
  <context>
Design spec §7 gives `'hard_delete' => 'guard' | 'warn' | 'allow'` with `guard` as the default, and
`.planning/REQUIREMENTS.md` SYNC-04 defines exactly one of them: *"`hard_delete` defaults to `guard`,
which skips and logs."* Neither document says what `warn` or `allow` do. `allow` reads unambiguously
as "go ahead and archive". `warn` does not.

Two readings are defensible and they differ in the action taken, not merely in a log level:

The package's standing rule is that when the spec is silent we ask rather than invent
(`CLAUDE.md`), which is why this is a gate rather than a judgement call in the next task. HubSpot's
delete is `archive()` and **there is no unarchive endpoint** — an archive this package issues can
never be programmatically undone, which is why the safe reading and the loud reading are not
interchangeable.

Whichever is chosen, `.planning/REQUIREMENTS.md` SYNC-04's acceptance text gains the definition, so
the next reader is not left deriving it again.
  </context>
  <options>
    <option id="warn-skips-loudly">
      <name>`warn` skips, exactly as `guard` does, but logs at warning level rather than info</name>
      <pros>No configuration value can cause an irreversible archive except the one literally named `allow`; the two safe values differ only in how visible they are, which is easy to reason about under an incident</pros>
      <cons>`guard` and `warn` take the same action, so the three values are really two actions and a log level</cons>
    </option>
    <option id="warn-archives-loudly">
      <name>`warn` archives, and logs at warning level; `allow` archives silently</name>
      <pros>Three values, three distinct behaviours; `warn` becomes the useful middle setting — mirror the delete, but make it impossible to miss in the logs</pros>
      <cons>An operator who reads `warn` as "warn me instead of doing it" gets an irreversible archive; the failure is silent until someone reads the CRM</cons>
    </option>
  </options>

  <action>
**`Sync\DeletePolicy`.** A `final` class whose resolution method takes four primitives — a bool for
whether the model uses `SoftDeletes`, the event name, the configured `hard_delete` value and the
configured `on_restore` value — and returns an action. Never the Eloquent model: the whole point of
the primitive signature is that the combinatorial table is a deterministic unit test with no
application, no database and no fake. Model the action as a backed enum rather than a string, for the
reason the association category is one: an enum case makes the invalid value unrepresentable past
construction, so no consumer downstream re-checks or trusts a string. Unrecognised `hard_delete` or
`on_restore` values throw through new `ConfigurationException` factories —
`unknownHardDeletePolicy()` and `unknownRestorePolicy()` — each listing the supported values from a
method, not a constant.

**`Sync\ArchiveHubspotObjectJob`.** A separate job rather than a mode flag on
`SyncHubspotObjectJob`: a mode parameter would make the HTTP verb depend on a constructor argument,
which is the shape `04-CONTEXT.md`'s Phase 2 note already rejected for the labelled association write.
Same primitives as the sync job — `ShouldQueue`, `Queueable`, `InteractsWithQueue`,
`SerializesModels`, `Batchable`, `deleteWhenMissingModels = true` — and it archives by the link row's
stored HubSpot id. It does not resolve a property map. It must not fail loudly when the link row is
already gone: an archive with nothing to archive is a completed archive, and it logs rather than
throwing.

**Three handlers on `Sync\HubspotObserver`,** each reusing 04-05's gate so `'deleted'`'s opt-in status
and `auto_sync.enabled` still apply:

- `trashed()` — a genuine soft delete. Archives.
- `forceDeleted()` — a hard delete of a `SoftDeletes` model. Follows `DeletePolicy`.
- `deleted()` — gated on the model NOT using `SoftDeletes` at all. Follows `DeletePolicy`. The gate is
  what stops it double-firing, because `forceDelete()` calls `delete()` internally and `delete()`
  always dispatches `deleting`/`deleted` regardless of soft or hard. Detect the trait's presence with
  `class_uses_recursive()` or `method_exists($model, 'forceDelete')` rather than by inspecting
  `deleted_at`, which is already set in memory by the time the handler runs.
- `restored()` — owns the entire response to a restore, as 04-05's `updated` guard promised. It logs,
  sets the link row's `is_stale` and `stale_at`, and **never** nulls `hubspot_id`; there is no
  unarchive endpoint, so keeping the id is what leaves re-linking possible. `on_restore => 'recreate'`
  is the opt-in that forks CRM history and must be explicit — implement it if the resolver's action
  covers it, and if it is deferred, say so in the docblock naming where it goes rather than leaving
  the config value undefined.

**`SyncHubspotObjectJob`** gains one early return: when the re-fetched model is trashed, log and stop.
Docblock the reason — `SerializesModels` restores soft-deleted models, so a job queued before a soft
delete arrives with the model trashed, and the delete path already owns that record's archived state.
This closes the item `04-CONTEXT.md` deferred to the planner; record the decision in the summary.

**`config/hubspot.php`** gains `auto_sync.hard_delete` defaulting to the guard value and
`auto_sync.on_restore` defaulting to the log value, each with a comment block in this file's voice
stating what the values do — including whichever `warn` semantics task 1 selected — that HubSpot's
delete is an archive with no unarchive endpoint, and that the recreate option forks CRM history and is
therefore never a default. Plain scalars only; no closure.

Also amend `.planning/REQUIREMENTS.md` SYNC-04's acceptance text with `warn`'s and `allow`'s
definitions, in a separate `docs(04-06):` commit.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local delete → irreversible CRM archive | HubSpot has no unarchive endpoint; this crossing cannot be walked back by this package |
| queue worker → a model whose local state changed since dispatch | `SerializesModels` re-fetches, and a soft-deleted model comes back trashed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-23 | Tampering | delete-event selection | critical | mitigate | Three distinct events — `trashed`, `forceDeleted`, and `deleted` gated on the absence of `SoftDeletes` — rather than a `trashed()` branch inside `deleted`. The in-memory `deleted_at` is already set when `deleted` runs during `forceDelete()`, so the naive check misclassifies a hard delete as a soft one and archives twice |
| T-04-24 | Tampering | `restored` nulling `hubspot_id` | high | mitigate | The flag is set, the id is not touched, and the test asserts the id byte-identical rather than merely asserting the flag. Nulling it strands the CRM record with no path back to the local row |
| T-04-25 | Tampering | property push to an already-archived record | medium | mitigate | `SyncHubspotObjectJob` returns early on a trashed model; the delete path owns the archived state |
| T-04-26 | Tampering | an unrecognised `hard_delete` value silently defaulting | high | mitigate | `ConfigurationException::unknownHardDeletePolicy()` lists the supported values and throws. A fallback to `allow` would issue irreversible archives from a typo; a fallback to `guard` would silently stop mirroring deletes an operator believed were mirrored |
| T-04-27 | Denial of Service | double archive on a force delete | medium | mitigate | The absence-of-`SoftDeletes` gate on `deleted`, asserted by a force-delete test counting requests |
</threat_model>
