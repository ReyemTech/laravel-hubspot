<objective>
Expand the tracer's single `create()` into the whole generic object core: create, update, upsert,
find, delete, search and batch — over any CRM object type, standard or custom, through one set of
classes.

Purpose: this is the founding architectural bet and success criterion 1. The competing package
needs roughly 500 hand-written lines per object type; the SDK's generic objects API needs none,
and this plan proves it by exercising eight object types through one gateway instance. It also
closes the HTTP 207 trap, where a partially failed batch returns a normal typed response and a
naive wrapper reports success while records silently never reach HubSpot.

Output: the full `ObjectGatewayContract` surface, the package-owned page/search/batch result
shapes, and the tests that prove both the generality and the partial-failure handling.
</objective>

## Verified SDK signatures — read from the installed 14.1.0, do not re-derive

Single object, `crm()->objects()->basicApi()`:
- `archive($object_type, $object_id)` — this is the delete. There is no unarchive endpoint anywhere
  in the SDK. Archived records are readable via `getById(..., archived: true)` and restorable only
  in the HubSpot UI.
- `create($object_type, $simple_public_object_input_for_create)`
- `getById($object_type, $object_id, $properties, $properties_with_history, $associations, $archived, $id_property)`
- `getPage($object_type, $limit, $after, $properties, $properties_with_history, $associations, $archived)`
- `update($object_id, $object_type, $simple_public_object_input, $id_property)` — note the object id
  comes FIRST here and second everywhere else. This is an SDK inconsistency and a live footgun.

Search, `crm()->objects()->searchApi()`:
- `doSearch($object_type, $public_object_search_request)` with
  `Model\PublicObjectSearchRequest`, `Model\FilterGroup`, `Model\Filter`.

Batch, `crm()->objects()->batchApi()`:
- `create($object_type, BatchInputSimplePublicObjectBatchInputForCreate)`
- `read($object_type, BatchReadInputSimplePublicObjectId, $archived)`
- `update($object_type, BatchInputSimplePublicObjectBatchInput)`
- `upsert($object_type, BatchInputSimplePublicObjectBatchInputUpsert)`
- `archive($object_type, BatchInputSimplePublicObjectId)`

**There is no single-object `upsert()`.** `BasicApi` has archive, create, getById, getPage and
update, and nothing else. Single-record upsert must be a one-item batch call.

**HTTP 207 is partial success, not failure.** The generated batch methods switch on status with
three branches: 201 gives `BatchResponseSimplePublicObject`, **207 gives
`BatchResponseSimplePublicObjectWithErrors`**, and default gives `Model\Error`. 207 is in the 2xx
family so Guzzle does not throw for it. The `WithErrors` model carries `status`, `num_errors`,
`errors` (a `StandardError` list) and `results` (the records that did succeed).

Single-object calls declare a `Model|Error` union and batch calls a three-way union. Narrow every
one of them with `instanceof`. A suppression here is forbidden — narrowing was reproduced against
PHPStan level max and clears the error with zero suppression comments.

## Deliberate non-goals in this plan

- **No object-type validation or normalisation.** `ObjectSerializer::toPathValue()` URL-encodes the
  string and nothing else; there is no allow-list anywhere in the SDK. Normalising `deals`,
  `line_items` and `p_custom` to canonical identifiers is `HubspotObjectType`'s job in Phase 3
  (REG-01). Do not write a validator here, and do not write a test asserting one exists.
- **No association writes during object creation.** `SimplePublicObjectInputForCreate` supports an
  inline `associations` field, and using it would create a second, ungoverned path for writing
  associations that bypasses the directed-pair primitive and Phase 3's registry. Keep object
  creation and association writes as two separate gateway calls.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04 | Tampering | `Gateway\ObjectGateway` batch methods | high | mitigate | Explicit `instanceof` narrowing of the 207 `WithErrors` branch into a `BatchResult` that surfaces partial failure; a test drives a real 207 body and asserts the errors are visible. Silently treating 207 as success is data loss that looks like success |
| T-02-05 | Tampering | `Gateway\ObjectGateway` single-object response handling | medium | mitigate | `instanceof` narrowing of the `Model|Error` union before reading an id, so a malformed response throws rather than yielding a wrong object id (D-34's rationale) |
| T-02-10 | Tampering | `update()` argument order | medium | mitigate | The SDK's `update()` takes the object id before the object type while every sibling method takes the type first; the test asserts the recorded request URI rather than the call site, so a transposition fails the build instead of writing to the wrong record |
| T-02-11 | Denial of Service | N+1 request patterns | medium | mitigate | Batch endpoints used wherever HubSpot offers one, with exact request-count assertions — an N+1 is a test failure, not a code smell (D-23) |
| T-02-SC | Tampering | composer installs | high | mitigate | Zero package installs; `tests/Ci/ComposerManifestTest.php` guards the seven-require limit (D-02) |
