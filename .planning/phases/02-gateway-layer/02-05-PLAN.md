## Scope boundary — read before designing the resolver

This phase resolves nothing about type ids on its own. It accepts a directed pair and, for a
labelled association, whatever the bound resolver returns for that exact direction. The registry
is Phase 3. The seam must let Phase 3 plug a real resolver in **without changing the gateway's
public shape** — that is the acceptance test for the design of this task.

## Verified SDK facts

`crm()->associations()->v4()->basicApi()->create($object_type, $object_id, $to_object_type,
$to_object_id, $association_spec)` where `$association_spec` is an **array** of
`HubSpot\Client\Crm\Associations\V4\Model\AssociationSpec` — a from/to pair can legitimately carry
more than one label at once. Each spec carries `association_category` (one of `HUBSPOT_DEFINED`,
`USER_DEFINED`, `INTEGRATOR_DEFINED`) and `association_type_id`.

## The bidirectional parameter — a deliberate decision, recorded

GW-02's acceptance names `associate($from, $to, label:, bidirectional:)` as the surface.

**AMENDED 2026-07-27 — the §6.4 probe has been RUN and this parameter's default is now measured.**
This section previously said the probe was blocked on a developer token and that the default must
therefore stay explicitly unresolved (a nullable boolean defaulting to null). That is obsolete.
FOUND-03 was answered against a developer test account: writing one directed association makes the
inverse direction readable immediately, with its own distinct type id, for both HubSpot's unlabelled
default and a user-defined paired label. Full results and raw response bodies:
`docs/probes/association-inverse-probe.md`.

**The default is therefore `false` — a plain non-nullable `bool`, not `?bool`.** HubSpot already
maintains the other direction, so a second write is redundant by default. Do NOT ship a nullable
parameter, and do NOT write a docblock saying the probe is blocked; both would be false as of
2026-07-27.

The parameter still ships, for the reason it always did: adding a parameter to an interface method
later is a breaking change for implementers, and interfaces are this package's documented extension
point under final-by-default (decision #5). It remains meaningful at `true` — HubSpot's automatic
inverse was observed on one object-type pair in one portal on one date, and a caller who wants the
reverse direction written explicitly (belt and braces, or a portal that behaves differently) can ask
for it. The probe set the default, not the shape — exactly as the design spec said it would.

What the parameter must NOT do is guess. Requesting both directions performs two independently
resolved directed writes; it never performs one write and assumes the inverse materialised.
