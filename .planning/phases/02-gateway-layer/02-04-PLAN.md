<objective>
Make writing an association backwards structurally impossible: introduce `ObjectRef` and
`AssociationPair(from, to)` as the only shape any association method accepts, and ship the
unlabelled write path — `createDefault()` — which resolves no typeId at all and therefore cannot
pick the wrong one.

Purpose: this is the first half of success criterion 2 and the reason the package exists in its
current shape. HubSpot's association type ids differ in each direction — Contact to Company is 279
and Company to Contact is 280, Note to Contact is 202 and Contact to Note is 201 — and the failure
mode is silent: the wrong direction is written and nobody notices for months. The unlabelled path
is the safest path precisely because it involves no id at all, so it ships first.

Output: the directed-pair primitive with a test that fails if its two sides ever stop being named
`from` and `to`, the association gateway's unlabelled write, dissociate and read, and the `Unit`
testsuite registration that makes pure value-object tests actually run.
</objective>

## The four binding rules — do not soften any of them

1. The primitive is a directed pair. No API in this package may accept two objects without an
   order. The note-to-contact mistake must be *unrepresentable*, not merely discouraged. If a
   signature lets a caller pass two objects without an order, that signature is wrong.
2. Unlabelled associations never resolve a typeId. `createDefault()` lets HubSpot pick the default
   for that direction — no id, no lookup, no chance of using the inverse.
3. A type that cannot be resolved for the requested direction throws, naming that direction, and
   never falls back to the inverse id. (Plan 02-05 owns this; do not pre-empt it here.)
4. The inverse is stored, never assumed.

## Verified SDK signatures — read from the installed 14.1.0

`crm()->associations()->v4()->basicApi()`:
- `createDefault($from_object_type, $from_object_id, $to_object_type, $to_object_id)`
- `create($object_type, $object_id, $to_object_type, $to_object_id, $association_spec)`
- `archive($object_type, $object_id, $to_object_type, $to_object_id)`
- `getPage($object_type, $object_id, $to_object_type, $after, $limit)`

Note the naming inconsistency: `createDefault` names its first pair `from_object_type`/
`from_object_id` while `create`, `archive` and `getPage` name theirs `object_type`/`object_id`.
The positional meaning is identical — the first pair is always the **from** side — but the
inconsistent naming is exactly the kind of thing that invites a transposition. Assert the recorded
request URI, not the call site.

`getPage` returns `CollectionResponseMultiAssociatedObjectWithLabelForwardPaging`, whose items are
`MultiAssociatedObjectWithLabel`. Read that model before writing any fixture body.

There is no method anywhere in this namespace that accepts two unordered objects. The directional
guarantee is already true at the SDK boundary; `AssociationPair` exists to make it equally true at
this package's own boundary, so a caller cannot bypass it by assembling ids directly.

## The Unit testsuite — a trap to handle carefully

`tests/Pest.php` already applies `TestCase` to `Feature` and `Unit`, but `phpunit.xml.dist`
declares only `Feature`, `Ci` and `Arch`, and `tests/Ci/PhpunitTestsuitesTest.php` asserts exactly
that set with a canonicalising comparison. A test file placed under `tests/Unit/` today would
silently never run in a bare `vendor/bin/pest` — the same class of bug 01-07 fixed for `Arch`.

Registering the suite and adding the first unit test must happen together: `phpunit.xml.dist` runs
with `failOnWarning` enabled, so a declared testsuite with no test files is itself a build failure.
Update `tests/Ci/PhpunitTestsuitesTest.php`'s expected set in the same commit.
