  <name>Checkpoint: confirm the first_wins tie-break rule before the calculator's shape ships</name>

  <decision>
The `first_wins` / `last_wins` tie-break rule when two signals share an `occurred_at`, and the
confirmation that `flushed_at` never enters the maths.
  </decision>

  <context>
`06-CONTEXT.md` delegates the tie-break explicitly: *"not discussed; pick a deterministic rule and
state it."* It is being surfaced rather than decided silently because it is **one-way in the same
sense D-10 is**: once installs have computed and written first-touch values under a rule, changing
the rule changes what HubSpot holds for every existing subject, and there is no read-back to
reconcile against (D-40 forbids one outside the `reconcile` modifier).

Two signals sharing an `occurred_at` is not a corner case here. `Carbon::now()` at second precision
makes it reachable for two rapid events, and a caller supplying an identical timestamp for a batch
of events makes it ordinary.

`06-RESEARCH.md` Pitfall 3 and `06-PATTERNS.md` both recommend option A. D-10 itself is locked and
is not being reopened — the confirmation below is of the tie-break rule that ships alongside it.
  </context>

  <options>
    <option id="option-a">
      <name>Break ties on the buffer row's own id — lowest id wins first_wins, highest wins last_wins</name>
      <pros>Deterministic; needs no new column; matches the ordering an auto-incrementing primary key already gives; insertion order is the only tie-break the buffer can observe without asking the caller for more; recommended by both RESEARCH and PATTERNS.</pros>
      <cons>Insertion order is not always the true event order — an app that buffers two events out of order gets the buffer's order, not the world's. Mitigated by the fact that the app also supplied the identical `occurred_at` that created the tie.</cons>
    </option>
    <option id="option-b">
      <name>Break ties on the signal's position in the input iterable</name>
      <pros>No dependency on a database column at all, keeping the calculator's inputs narrower.</pros>
      <cons>Not deterministic across queries — the same rows in a different result order produce a different first-touch value, which is exactly the instability the ordering edge exists to forbid. Rejected unless the developer prefers it.</cons>
    </option>
    <option id="option-c">
      <name>Refuse the tie — throw when two signals matching one first_wins rule share an occurred_at</name>
      <pros>No silently-wrong answer; forces the app to disambiguate.</pros>
      <cons>Turns an ordinary second-precision collision into a failed flush for the whole subject; the feature exists to capture attribution, not to refuse it.</cons>
    </option>
  </options>

  <resume-signal>Select: option-a, option-b, or option-c. Reply "option-a" to take the recommended rule.</resume-signal>

  <action>
Complete `compute(iterable $signals, array $rules): array<string, string>` where `$rules` is
`array<string, MergeRule>` keyed by HubSpot property name.

Keep the class a pure function of its two arguments: no constructor, no injected clock, no config
read, no container, no Gateway, no `Illuminate\Database` reference. The only framework name it may
carry is `Illuminate\Support\Collection`, and only because D-08's `SignalCalculator::__invoke()`
signature requires it. This is SIG-04's whole point, and it is what lets the unit test file boot
nothing.

Dispatch on `MergeRule::verb()` with one branch per verb and one for the invokable case. Never
re-parse a declaration string here — `MergeRule` is the single parser (STANDARDS §6b), and a second
parse is how the two would drift.

Verb semantics, each with its own test:

- `first_wins` — the field value from the earliest matching signal, and never replaced once a value has been found. The immutability is the behaviour, not an implementation detail; Test 2 pins it separately from Test 1 for that reason.
- `last_wins` — the field value from the latest matching signal. There is no `overwrite` verb; it was an earlier draft's name for this same operation.
- `increment` — the count of matching signals, as a string. It takes no field and ignores properties entirely.
- `sum` — the numeric total of the named field across matching signals. Non-numeric values throw rather than coercing to zero: a silently-zeroed sum is a wrong absolute value written straight to HubSpot.
- invokable class-string — instantiate the class and call it with an `Illuminate\Support\Collection` of exactly the matching signals. Its return value is cast to a string for the property array.

Compute over ALL signals handed in, flushed or not. `flushed_at` marks what has been written and is
never an input to the maths (D-10) — excluding flushed rows would restart `increment` and `sum` at
zero on the second flush and overwrite a correct HubSpot value with a partial one, turning absolute
roll-ups into accidental deltas. Write that reasoning into the class docblock, and let Tests 8 and 9
be what proves it rather than the comment.

Keep the supported verb list as a `validVerbs()` METHOD, never a `const array`, for the reason
`ServiceProvider::consoleCommands()`'s docblock gives: a const declaration has no executed line
`pest --mutate` can attribute a covering test to, so dropping a verb would score as an uncovered
mutant instead of a caught defect. This class is where the 80% MSI floor is meant to bite hardest.

Create `tests/Support/Signals/BufferedSignal.php`: a final readonly value object carrying `int $id`,
`string $signalName`, `array $properties`, `DateTimeImmutable $occurredAt` and
`?DateTimeImmutable $flushedAt`. Constructed in memory, so `tests/Unit/Signals/RollUpCalculatorTest.php`
needs no database, no fake and no Testbench application boot.
  </action>
