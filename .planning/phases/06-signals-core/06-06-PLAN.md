Build one record per subject as `['id' => <id_property value>, 'properties' => [...]]`, sorted by
`(subject_type, subject_id)` so a replayed flush sends an identical body. If two subjects produce
the same `id` value, throw `ConfigurationException::duplicateSignalSubjectIdentifier()` naming the
`id_property`, the colliding value and both subjects, before any request — HubSpot would otherwise
merge two people's roll-ups into one record and report success.

Write with `foreach (array_chunk($records, 100) as $chunk)` and one
`$gateway->upsertMany($objectType, $idProperty, $chunk)` per chunk. Read results through
`recordsDespitePartialFailure()` and pair it with `errors()` for targeted logging. Never call the
singular `upsert()`: it wraps `upsertMany()` with a single-element array and reads through the
strict `records()` accessor, which throws on any 207 and would abandon the 99 subjects that
succeeded alongside the one that failed. Calling it once per subject inside a loop would also make
each call its own HTTP request, which is precisely the "N, not one" that SIG-06 forbids.

Then, per subject that the batch confirmed: append each of its unflushed rows to the configured
`SignalStore`, and only after that set `flushed_at` on those rows. The order is the idempotency
guarantee — a job that dies between the write and the trail append is retried by the queue and
simply redoes idempotent work, whereas marking rows flushed first would lose the trail permanently.

Introduce no claim, no lease and no lock (D-06). Overlapping and retried flushes are harmless by
construction: roll-ups are absolute, trail appends are keyed on the source row id, and `flushed_at`
gates nothing the maths reads. Write that into the class docblock, naming why the neighbouring
`DatabaseWebhookEventStore` claim machinery is deliberately not adapted here — a redelivered webhook
drives side effects that are not naturally idempotent, and a trail append does not.

Queue retry and backoff follow this package's existing queued-job conventions; do not invent a new
retry policy for this job.

Signals never names a `HubSpot\*` type. `ObjectGatewayContract` translates every SDK exception before
returning, so a HubSpot rejection arrives as `ApiException` and is retried by the queue. Test 13
pins that no SDK type appears in the chain.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `hubspot_signals` → HubSpot API | The only outbound network crossing in the phase. Computed absolute values leave the process and overwrite whatever the portal holds. |
| queue payload → worker process | Subject identifiers cross a serialization boundary and are rehydrated in a different process, possibly minutes later. |
| HubSpot 207 response → package state | A partial-success response decides which subjects get a trail entry and a `flushed_at`. |
