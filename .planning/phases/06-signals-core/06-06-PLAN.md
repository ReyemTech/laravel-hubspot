<objective>
Complete `FlushSignalsJob`'s write path: grouped and chunked so the request is expressible at all,
and serialized per subject so two overlapping flushes cannot lose an update.

Purpose: this is the phase's only outbound network path and the requirement with the most ways to be
quietly wrong. Two of those ways were shipped in this plan's own first draft and caught by automated
review of PR #81, which is why both are now the plan's centre of gravity rather than a footnote:

1. **An ungrouped chunk cannot be sent.**
   `ObjectGatewayContract::upsertMany(string $objectType, string $idProperty, array $records)`
   carries one object type and one id property per request. "Chunk at 100 across subjects" was
   written against a Phase 4 precedent's prose rather than against the signature it would be called
   through.

2. **Absolute values do not make concurrency safe.** They make a *retry of the same input* safe.
   Two workers computing over *different row sets* is a different situation, and it loses updates:
   worker A reads rows {1,2} and computes 2; worker B reads {1,2,3}, computes 3, writes 3 and marks
   all three flushed; worker A then writes its stale 2 over B's 3, permanently, with no unflushed
   rows left to repair it. Trail dedup does not order the property write, `reconciled_at` does not
   order it, and scheduler `withoutOverlapping()` cannot help because SIG-06 *requires*
   `identify()` to dispatch a flush that races the scheduled one.

Output: the grouped-and-chunked write, the per-subject atomic claim with its lease, the claim
migration, and `hubspot.signals.flush_lease`.
</objective>

calculate-and-write, decided on affected row count. Its reversibility rating is **one-way**: *"the
trail's unique key and the claim column ship in migrations; changing either later needs a migration
against installed data."* The trail half was settled by 06-05's checkpoint. This settles the claim.

**What is not in question:** that a claim exists, that it is per subject, that the decision is made
on affected rows rather than on a prior read, and that `Webhooks\Stores\DatabaseWebhookEventStore`
is the shape to copy (SHAPE ONLY — `Signals` may not import from `Webhooks`, R7). The public surface
is fixed either way: `FlushClaims::claim()` returns `SubjectFlushClaim::Acquired` or
`SubjectFlushClaim::Held`, and `FlushSignalsJob` skips a `Held` subject. Only the storage differs.

**Why this needs deciding rather than inferring.** D-06's wording — *"a conditional UPDATE claims a
subject's unflushed rows"* — reads most naturally as a column on `hubspot_signals`. Written that way
literally, it does not actually close the lost update, and that is worth stating plainly before a
migration ships: worker A claims rows {1,2}; row 3 is then inserted, unclaimed; worker B's
conditional UPDATE matches row 3 and affects one row, so B believes it claimed the subject. Whatever
B then computes over — its own row only, or all rows — one of the two workers writes a value that
does not reflect the full set, and both mark rows flushed. A newly inserted row is always claimable,
so a per-row predicate can never give per-SUBJECT exclusion on its own. The claim has to be keyed on
the subject's identity, or it has to be made all-or-nothing by a second statement.

Whichever option is chosen, it ships as a NEW migration file in `database/migrations/signals/`, so
06-01's own `hubspot_signals` migration is never rewritten by a later plan.

`hubspot.signals.flush_lease` (seconds) exists in all three options, mirroring
`hubspot.webhooks.claim_lease`, so a worker that dies holding a claim does not strand its subject.
  </context>

  <action>
Widen `FlushSignalsJob` from 06-01's single-subject path to D-05's cross-subject batch. The
constructor keeps taking `list<array{subjectType: class-string, subjectId: string}>` — identifiers
only. `identify()` dispatches it with a list of one element and the scheduled command dispatches it
with up to 100; they are the SAME code path, which is what keeps the singular case from becoming a
second implementation.

`handle()` resolves `ObjectGatewayContract`, `BoundModelReader`, `SignalMap`, `RollUpCalculator` and
`Contracts\SignalStore` as typed method parameters — resolved by the queue worker, never in the
constructor, so nothing resolvable-only-at-runtime is serialized.

Per invocation: reload each subject's buffer rows fresh from `hubspot_signals`, including rows whose
`flushed_at` is already set, because roll-ups are absolute and computed over everything (D-10).
Compute each subject's properties through `RollUpCalculator::compute()` with the rules
`SignalMap::rulesFor()` returns.

**Group before you chunk, and group on the PAIR.** Resolve each subject's
`Signals\BoundSignalSubject` through `BoundModelReader::for()` and bucket the built records by the
`(objectType, idProperty)` pair it carries — both halves, not the object type alone, because
`hubspot.models` explicitly permits two models to bind to the same object type under different id
properties (`config/hubspot.php`'s own worked example binds `Lead` and `HealthCheckIntake` both to
`contacts`, on `email` and `intake_email`). Then, per group, `array_chunk($records, 100)` and issue
one `$gateway->upsertMany($objectType, $idProperty, $chunk)`. The request count is
`sum(ceil(groupSize / 100))` across the groups covered; write that expression into the class
docblock and assert it in Test 6 as an expression rather than as a literal.

**Do not refuse a multi-object-type batch.** An earlier draft of this plan resolved the same problem
by throwing when a flush's subjects spanned more than one object type. That is not what SIG-06's
"one batch write per flush (not N)" asks for — grouping satisfies it, and refusing would make the
scheduled command's own natural selection (every pending subject) unrunnable on any install with two
bound models. Multi-object SUBJECTS — one subject carrying signals for several object types — remain
deferred to Phase 7 and are a different thing.

Read every result through `recordsDespitePartialFailure()` and pair it with `errors()` for targeted
logging. Never call the singular `upsert()`: it wraps `upsertMany()` with a single-element array and
reads through the strict `records()` accessor, which throws on any 207 and would abandon the 99
subjects that succeeded alongside the one that failed. Calling it once per subject inside a loop
would also make each call its own HTTP request, which is precisely the "N, not one" SIG-06 forbids.

Sort records within each group by `(subject_type, subject_id)` and iterate the groups in a
deterministic order — sort the group keys — so a replayed flush sends identical bodies in an
identical sequence. If two subjects **within one group** produce the same `id` value, throw
`ConfigurationException::duplicateSignalSubjectIdentifier()` naming the object type, the
`id_property`, the colliding value and both subjects, before any request in that group is issued;
HubSpot would otherwise merge two people's roll-ups into one record and report success. Scope the
check to the group: the same string under two different id properties identifies two different
records and is not a collision, which Test 13 pins.

Then, per subject the batch confirmed: append each of its unflushed rows to the configured
`SignalStore`, and only after that set `flushed_at` — `WHERE id IN (...) AND flushed_at IS NULL`
over exactly the row ids this calculation read, never a blanket subject-scoped UPDATE. The append
order is the retry guarantee: a job that dies between the write and the trail append is retried and
redoes idempotent work, whereas marking rows flushed first would lose the trail permanently. The
explicit id list is a separate guarantee: a row inserted mid-flush stays unflushed and repairs the
value on the next run.

Queue retry and backoff follow this package's existing queued-job conventions; do not invent a new
retry policy for this job.

Signals never names a `HubSpot\*` type. `ObjectGatewayContract` translates every SDK exception before
returning, so a HubSpot rejection arrives as `ApiException` and is retried by the queue. Test 17
pins that no SDK type appears in the chain.

Concurrency is Task 2's subject. Write nothing in this task's docblocks about overlapping flushes
being safe — they are not yet.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `hubspot_signals` → HubSpot API | The only outbound network crossing in the phase. Computed absolute values leave the process and overwrite whatever the portal holds. |
| queue payload → worker process | Subject identifiers cross a serialization boundary and are rehydrated in a different process, possibly minutes later. |
| concurrent workers → one subject's properties | Two flushes may cover the same subject at once — the identify-triggered one and the scheduled one, which SIG-06 requires to be able to race. |
| HubSpot 207 response → package state | A partial-success response decides which subjects get a trail entry and a `flushed_at`. |
