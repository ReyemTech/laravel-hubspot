  <action>
Implement the `first_wins:<field>|reconcile` modifier inside `FlushSignalsJob`.

It is the single documented exception to D-40's buffer-first rule. Spec §5 states plainly that the
package never needs to ask HubSpot what the first touch was — it already knows — so the only read
this phase issues is this opt-in, per-property one, and it fires at most once per subject ever.

Placement: **inside the claim, before that group's write.** A read for a subject whose claim was not
acquired must not happen at all (Test 11) — a `Held` subject is skipped whole. Collect, per
`(objectType, idProperty)` group, the claimed subjects that have at least one `reconciles()` rule
AND a null `reconciled_at`. If that set is empty for a group, issue no read for it. If it is not,
issue ONE `findMany()` per group covering that group's whole set, requesting only the properties the
reconciling rules name. One read per group rather than one per subject is the same not-N discipline
the write side follows, and one read per GROUP rather than one overall is forced by the same
signature fact that forced the grouping: `findMany()` takes a single object type and a single
`$idProperty`.

For each reconciling property: if the portal already holds a non-empty value, that value wins over
the buffer's computed one; otherwise the buffer's value is used. That asymmetry is what "reconcile a
first touch" means — a value already recorded upstream is by definition earlier than anything this
buffer saw.

Set `reconciled_at` on the subject's rows as part of the same flush, on the same explicit row-id
list the `flushed_at` update uses, so a later flush's collection step finds nothing to read. The
gate is the column, not an in-memory flag: Test 10 clears the column and proves a read follows,
which is what stops a cached decision from surviving an Octane worker boundary or a second job
instance.

State the retry semantics explicitly in the docblock and assert them in Test 7, rather than leaving
a reader to infer them. "At most one read per subject, ever" is the requirement's own wording and it
has to survive a job that dies mid-flight.

**Record D-10's constraint on Phase 7 where Phase 7 will read it.** In `.planning/ROADMAP.md`, annotate
Phase 7's `hubspot:signals:prune` success criterion: because roll-ups compute over all rows including
flushed ones (D-10), deleting flushed rows for an IDENTIFIED subject silently shrinks `increment` and
`sum` on the next flush, and HubSpot is then overwritten with a smaller, wrong value. Phase 7's prune
must therefore either never delete identified rows, or materialise the roll-up before deleting them.
`retention_days` applies cleanly to UNIDENTIFIED rows, which is where the unbounded growth actually
comes from. Note in the same annotation that Phase 7's prune inherits a second table from 06-06 —
released flush claims — and a third from 06-05, the trail. This is a recorded constraint, not a
Phase 6 change of scope.
  </action>
