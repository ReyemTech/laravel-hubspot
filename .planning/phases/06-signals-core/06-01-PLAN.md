<objective>
Prove the whole Phase 6 architecture end-to-end on one thin path, and ship the buffer it rests on.

One `Hubspot::signal()` call reaches one `hubspot_signals` row with zero HTTP; one
`Hubspot::identify()` binds that row to a subject and dispatches `FlushSignalsJob`, which resolves
the subject through `config('hubspot.models')` and issues exactly one
`ObjectGatewayContract::upsertMany()` call. Every layer the phase touches — the architecture rule,
the config block, the migration, the recorder, the identity resolver, the calculator, the job, and
the facade — is wired for real on that single path.

Purpose: an architectural dead-end in Signals is discovered after one commit rather than after six
plans of horizontal layers. The layer-boundary rule alone is a hard blocker (see Task 1) that would
otherwise surface at the end of the phase with every Signals class already written against it.

Output: a working `signal() -> buffer -> identify() -> one batched write` path, `SIG-01`'s gated
migration with its directed missing-table error, and `SIG-02`'s zero-HTTP guarantee.

This tracer is production-quality, not a prototype. Its one path ships. `RollUpCalculator` supports
only the `increment` verb here — a functionality gap that plan 06-04 fills without changing its
shape. There are no architectural gaps: no stubbed gateway, no fake-only wiring, no TODO.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consuming app → `Hubspot::signal()` | Application-supplied `visitor_id`, `signal_name` and `properties` cross into package-owned storage. The app authorises the call; the package validates the shape. |
| `hubspot_signals` → HubSpot API | The only outbound crossing in the phase. Roll-up values computed from buffered rows leave the process through `Gateway`. |
| package → operator logs / exception messages | Directed error messages cross into an operator's log stream, which is a different audience from the data subject. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Tampering / DoS | `Signals\SignalRecorder::record()` | high | mitigate | Bound `visitor_id` and `signal_name` in BYTES against their `VARCHAR(191)` widths before the INSERT and throw rather than truncate. Truncation aliases two distinct visitors onto one buffer identity; an unbounded value fails the INSERT after the caller believed the call succeeded. This is PR #71's class, applied at the point data enters. |
| T-06-02 | Information disclosure | `ConfigurationException::missingSignalsTable()` and every Signals exception message | medium | mitigate | Directed messages name the table, the config key and the command — never a `visitor_id` value or a `properties` payload.
