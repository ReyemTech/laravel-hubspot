<objective>
Give the registry a durable store without giving every consumer a migration. Ship the database
store, the conditional migration loading that makes `composer require` a complete install, and the
directed error that a missing table produces instead of a raw SQL failure.

Purpose: zero-migration install is a named goal of the package (core spec §2 goal 5), and it is the
kind of promise that is easy to state and easy to break — one unconditional `loadMigrationsFrom()`
and every consumer inherits a migration they never asked for.

Output: an interchangeable database store, a publishable-but-not-published migration, and a missing
table that tells the developer what to run.
</objective>

## The schema REG-02 fixes

Columns: `from_object_type`, `to_object_type`, `type_id`, `category`, `label`, `inverse_type_id`,
`is_default`. **Direction unique against type id** — the constraint is what makes "two different
type ids for the same direction and label" unrepresentable rather than merely unlikely.

Each direction is its own row. A paired label carries a *different name* in each direction
(`Deals` forward, `People` inverse — FOUND-03 run 2), so a schema that stores one row per pair with
two id columns cannot represent reality and must not be built.

`inverse_type_id` is recorded for traversal and verification. 03-01 already proved it unreachable
from any write path; that guarantee must survive this plan, so re-run that test against the database
store rather than assuming it transfers.

## Zero-migration install is the delicate part

The contract: `composer require` gives a working package with no publish step and no `migrate`. The
default store is `cache`, so the default install touches no database at all.
`loadMigrationsFrom()` must fire **only** when a database store is active.

REG-03 notes a second consumer arriving in Phase 6: SIG-01's signal buffer gates the same way, on
`HUBSPOT_SIGNALS` rather than `HUBSPOT_STORE`. Build the conditional so a second gated migration
group is an obvious addition, not a rewrite — but do not build the signals side now.

Testbench makes this testable in both directions: assert the migration is absent from the loaded
paths under the default config, and present when the store is switched.
