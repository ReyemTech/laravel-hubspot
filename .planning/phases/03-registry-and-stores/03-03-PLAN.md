## The SDK class is not where REG-02 says, and it is not the Registry's to call

Verified in the installed 14.1.0 — read `03-CONTEXT.md` §1 before writing anything:

```
HubSpot\Client\Crm\Associations\V4\Schema\Api\DefinitionsApi::getPage($from_object_type, $to_object_type)
```

Note the **`Schema`** namespace segment, absent from REG-02's text. Two arguments, no paging
parameters. Returns `CollectionResponseAssociationSpecWithLabel|Error`, items being
`Schema\Model\AssociationSpecWithLabel` with `category` (string), `label` (string), `type_id` (int).

`Registry` may not name it (R1). So this plan adds a small Gateway collaborator that returns
package-owned `AssociationDefinition` values, and the command consumes those. Put it on its own
class, not on `AssociationGateway` — that class already owns the write path, and `ObjectGateway` at
426/500 lines is the standing lesson about appending.

Narrow the response union and throw `ExceptionTranslator::unexpectedResponseShape(...)` on anything
unexpected: the `case 200 / default → Model\Error` switch returns before the SDK's own non-2xx throw,
so an unexpected 2xx deserialises to `Error` silently. This caught PR #18 and PR #19 already.

## What the sync must not do

A paired label carries a **different name in each direction** — `Deals` forward, `People` inverse
(FOUND-03 run 2). `getPage($from, $to)` answers for one direction only. So reconciling a pair means
**two calls**, and each direction's row carries its own label and its own type id. A sync that calls
once and writes both directions is the bug this phase exists to prevent, wearing a different hat.

**Do NOT infer `inverse_type_id` by pairing up the two reads** (Codex P1 on PR #22). This plan
originally said to record it "from the opposite direction's read", and that is not derivable. Each
returned item carries only `category`, `label` and `type_id` — verified against
`Schema\Model\AssociationSpecWithLabel` — and a paired label deliberately has a *different name* in
each direction. So with two or more user-defined pairs on one direction, say `Deals`/`People` and
`Sponsor`/`Sponsored by`, the forward list `[1:"Deals", 5:"Sponsor"]` and the reverse list
`[2:"People", 6:"Sponsored by"]` contain **no join key**. Matching by position or by "the only other
user-defined one" would silently persist another label's id as `inverse_type_id`.

So: **leave `inverse_type_id` null unless it has actually been observed.** The sync records each
direction's own row from its own read and nothing more. The only honest source for the pairing is
observation — writing an association and reading the other direction back, which is what FOUND-03
did and what `hubspot:associations:doctor` does in Task 3.

Before implementing, check whether a richer endpoint exposes the pairing explicitly (the
`DefinitionsApi::create`/`update` request models are worth reading, and there may be a labels
endpoint that returns both names). If one does, use it and record the finding. If none does, null is
the correct value and the doctor fills it in. **Test with a multi-label response whose items are
reordered**, so any positional assumption fails.

`inverse_type_id` must remain unreachable from write paths — re-run that guarantee after the sync and
after the doctor populate it.

## hubspot:doctor is deliberately partial

REG-04 wants it to report bound models, soft-delete status and resolved delete policy. **Model
binding is Phase 4.** Per `03-CONTEXT.md` §3 this command ships reporting what exists — store per
concern, whether and when the registry was synced, how many directions it holds, which resolver is
bound — and **names the model section as not yet built**, with a test asserting that. Silently
omitting it would tell a developer they have no bound models when the feature does not exist.

**This plan therefore does not close REG-04, and must not tick it.** REG-04a (everything above, plus
`hubspot:associations:doctor` in full) completes here; REG-04b (the bound-model section) is Phase 4's.
Same for REG-01, whose local-id-resolution half is Phase 4's. Phase 3's close-out marks the Phase 3
halves done and leaves both requirements open, updating `.planning/STATE.md`,
`.planning/ROADMAP.md` and `.planning/REQUIREMENTS.md` **together** — Phase 2's close-out found those
three contradicting each other because only one was updated.
