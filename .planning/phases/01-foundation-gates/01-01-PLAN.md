<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Packagist -> local/CI vendor tree | Dependency resolution pulls third-party code that executes during `composer install` and during every test run |
| Pull request -> GitHub Actions runner | Untrusted contributor code executes in a workflow that has a repository token |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | `composer.json` require-dev resolution | high | mitigate | Every composer package installed here appears in 01-RESEARCH.md's Package Legitimacy Audit with an OK verdict, audited directly against the Packagist API. Re-verify each pin against the registry before committing rather than pinning from recall. `composer audit` becomes a required check in plan 07 |
| T-01-02 | Elevation of Privilege | `.github/workflows/ci.yml` | high | mitigate | Set `permissions: contents: read` at workflow level. The tests workflow triggers on `pull_request` and receives no secrets, so a malicious PR cannot exfiltrate a token or write to the repository |
| T-01-03 | Information Disclosure | test suite execution | medium | mitigate | D-12: the suite performs zero real network I/O and runs green with no credentials, so no token can be present to leak. Task 1 verifies this by running with no `.env` file |
| T-01-04 | Spoofing | GitHub Actions third-party actions | medium | mitigate | Use only `actions/*` and `shivammathur/setup-php`, referenced by major version tag |
| T-01-SC | Tampering | composer installs | high | mitigate | Package Legitimacy Audit clean for all composer packages — no `[ASSUMED]`, no `[SUS]`, no `[SLOP]` — so no blocking human checkpoint is required for this plan. The npm surface is gated separately in plans 03 and 06 |
</threat_model>
