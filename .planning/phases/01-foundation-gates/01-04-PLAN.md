<objective>
Encode the ten architecture rules and prove every one of them actually fails a build.

Purpose: this is the phase's highest-risk deliverable. 01-RESEARCH.md's finding that
`pest-plugin-arch` rules over an empty namespace pass **vacuously** is rated LOW confidence, and if
it is right, six layer-boundary rules written against six empty namespaces would report green while
proving nothing — six gates that exist only as decoration until someone notices in Phase 6. ROADMAP
Phase 1 criterion 2 is explicit that a deliberate violation fixture must fail the build for each
rule. That is not decoration either; it is the only thing that makes this deliverable real.

a recorded answer to the empty-namespace question.

<the_ten_rules>
From D-09 as amended by D-35, plus D-34 and D-19. `NS` is `ReyemTech\Hubspot`.

| # | Rule |
|---|------|
| R1 | `HubSpot\*` may be used **only** in `NS\Gateway` — no other layer may name an SDK class |
| R2 | `NS\Registry` may depend on `NS\Gateway` and nothing else in the package |
| R3 | `NS\Sync` may depend on `NS\Registry` and `NS\Gateway` |
| R4 | `NS\Webhooks` may depend on `NS\Registry` and `NS\Gateway` |
| R5 | `NS\Signals` may depend on `NS\Registry` and `NS\Gateway` |
| R6 | `NS\Frontend` may depend on the public facade only |
| R7 | `NS\Signals` may **not** depend on `NS\Sync` or `NS\Webhooks` — it is a peer, not a consumer |
| R8 | `NS\Frontend` may **not** reference `HubSpot\*`, `NS\Gateway`, `NS\Registry`, `NS\Sync`, `NS\Webhooks` or `NS\Signals` |
| R9 | Every PHP file declares `strict_types=1` |
| R10 | Config keys holding tokens and secrets never appear in log calls |

R6 and R7/R8 are deliberately both positive (`toOnlyUse`) and negative (`not->toUse`) forms of
overlapping constraints. Keep both: ROADMAP criterion 2 enumerates them separately, and the
negative form is what survives when a later phase widens the positive allowlist.

R10 is not a dependency rule and probably cannot be expressed through `pest-plugin-arch`. Implement
it as a Pest test that scans `src/` for the `hubspot.*` config keys holding a token or secret
appearing as an argument to a logging call. STANDARDS §10 requires it; D-19 is the decision.
</the_ten_rules>

  <behavior>
    - The harness enumerates one fixture per rule from `tests/Arch/Fixtures/`, keyed by rule id.
    - For each fixture it produces a tree in which that fixture is placed in its target layer directory, runs the architecture suite against that tree, and asserts the run exits NON-ZERO.
    - It exits non-zero, naming the rule, if any rule's fixture fails to make the suite red.
    - It exits non-zero if a rule declared in the rule manifest has no fixture — an unfired rule and a missing fixture are the same defect.
    - It never modifies the checked-out working tree; the working tree is byte-identical before and after, including after an induced mid-run failure.
  </behavior>
  <action>
Build the harness before the rules exist, run it, and commit it failing (D-13) — with no rules
written, every fixture fails to make the suite red, which is precisely the vacuous-pass condition
this harness exists to detect. That failing run is the evidence that the harness has teeth.

Write `scripts/ci/verify-arch-rules-fire.sh` with `set -euo pipefail`.

**The harness must not mutate the working tree.** Copying a violating class into `src/Signals/` and
deleting it afterwards is the obvious implementation and it is wrong here for two reasons: plan 05
runs in this same wave and analyses `src/` concurrently, and any crash between copy and delete
leaves a violation committed-adjacent in a developer's tree. Use a scratch checkout instead —
`git worktree add --detach` into a temporary directory, symlink `vendor/` into it, place the
fixture there, run the suite from there, then remove the worktree in a `trap`. Verify the
no-mutation property by hashing the tree before and after, including a run that is killed partway.

Keep the rule manifest in one place — a list of rule ids read by both the harness and
`tests/Arch/FiringHarnessTest.php` — so adding R11 in a later phase without a fixture fails
immediately rather than silently inheriting a proof it never earned.

Create `tests/Arch/Fixtures/` with one deliberately violating class per rule, each carrying a
header comment naming the rule it violates and stating that it is a fixture, never production code.
These live under `tests/` and are outside the `src/` PSR-4 root, so they cannot be autoloaded into
the package by accident.

Fixture shapes, one per rule: a class in a non-Gateway layer importing an SDK class (R1); a
`Registry` class importing from `Sync` (R2); a `Sync` class importing from `Webhooks` (R3); a
`Webhooks` class importing from `Sync` (R4); a `Signals` class importing from `Frontend` (R5); a
`Frontend` class importing from `Registry` (R6); a `Signals` class importing from `Sync` (R7); a
`Frontend` class importing an SDK class (R8); a PHP file with no strict-types declaration (R9); a
class passing a token config key into a logging call (R10).

Add `tests/Arch/FiringHarnessTest.php` asserting the manifest and the fixture directory agree —
every rule has exactly one fixture and every fixture maps to a declared rule.
  </action>
  <verify>
    <automated>bash -n scripts/ci/verify-arch-rules-fire.sh && vendor/bin/pest tests/Arch/FiringHarnessTest.php</automated>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Future contributor code -> package layer boundaries | Every later phase adds classes that could reach across a boundary; the rules are the only mechanical check |
| Package code -> log sinks | Tokens and client secrets must never cross into a log line (D-19) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Information Disclosure | R10, secrets in log calls | high | mitigate | `tests/Arch/SecretLoggingTest.php` scans `src/` for the named token and secret config keys appearing as arguments to logging calls, with a fixture proving the scan fires. STANDARDS §10 requires this; a leaked PAT in a consumer's log aggregator is a portal compromise |
| T-04-02 | Tampering | vacuously-green architecture rules | critical | mitigate | The firing harness proves each of the ten rules fails a build, and runs on every pull request rather than once. This is the difference between a gate and a comment claiming there is one |
| T-04-03 | Elevation of Privilege | R1/R8, SDK reachable outside Gateway | high | mitigate | R1 confines `HubSpot\*` to `Gateway` and R8 blocks `Frontend` from reaching it. Without R8 the frontend layer becomes a back door around the boundary that makes the SDK swappable, and around the trust checks that live behind it |
| T-04-04 | Tampering | harness mutating the working tree | medium | mitigate | The harness operates in a scratch `git worktree` with `trap`-based cleanup, verified by a before/after tree hash including an induced mid-run failure. A crashed harness cannot leave a violating class in `src/` |
| T-04-05 | Spoofing | `declare(strict_types=1)` absence | high | mitigate | R9 enforces strict types package-wide. D-34's justification is concrete: HubSpot object ids are strings that look like integers, and coercive typing makes `"0"`, `0` and `""` silently equivalent — a wrong id writes to the wrong CRM record |
</threat_model>
