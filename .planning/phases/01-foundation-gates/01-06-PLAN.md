<scope_boundary>
**This plan builds the site. It does not deploy it.**

FOUND-04's acceptance is that CI "builds the Astro + Starlight site in `site/`". SHIP-04, in
Phase 9, owns publishing to the `docs-pages` branch and the Pages deploy. `.planning/REQUIREMENTS.md`
tracks zero requirements duplicated across phases and that property is worth keeping.

The deploy is also in the blocked bucket: Pages needs a paid plan on private repositories, so a
`deploy-pages.yml` shipped now would be a workflow that has never once run — indistinguishable from
a broken one, and noise in the required-checks list plan 07 reconciles.

Task 2 therefore records the procedure rather than executing it. That is not deferral: the
reference implementation is being read now, while it is cheap, so Phase 9 is a wiring job instead
of a rediscovery.
</scope_boundary>

`GITHUB_TOKEN`, so a `GITHUB_TOKEN`-authored push to `docs-pages` succeeds while the Pages deploy

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry -> repository | Astro and Starlight and their transitive tree execute at install and build time |
| Pull request -> GitHub Actions runner | Untrusted contributor content is built by the docs workflow |
| Build output -> published site | Anything the build embeds becomes publicly readable once Phase 9 deploys |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-SC | Tampering | npm installs (`astro`, `@astrojs/starlight`) | high | mitigate | Both returned SUS from the legitimacy gate. Blocking human checkpoint above verifies each registry page and repository link before install; `pnpm-lock.yaml` is committed and CI installs with `--frozen-lockfile` |
| T-06-01 | Elevation of Privilege | `.github/workflows/docs.yml` | medium | mitigate | `permissions: contents: read`, triggered on `pull_request`, consumes no secrets. The build runs contributor-authored MDX, so it must never hold a write token |
| T-06-02 | Information Disclosure | future published site content | medium | mitigate | Recorded in `docs/repo/docs-site-deploy.md`: everything under `site/` becomes public on deploy. No credential, portal id or internal URL belongs in the content tree |
| T-06-03 | Denial of Service | docs deploy silently never firing | medium | mitigate | The PAT-rather-than-GITHUB_TOKEN rationale is recorded with its failure mode, because the symptom is a green pipeline and a stale site — nothing reports it (D-46) |
| T-06-04 | Tampering | `docs-pages` branch losing its own `.github/` | high | mitigate | The preserve-list mechanism and the reason `.github/` is in it are recorded. Wiping it kills the deploy trigger while the push still succeeds |
</threat_model>
