  <action>
Create `release-please-config.json` and `.release-please-manifest.json` using `release-type:
simple`, with `version.txt` as the version source.

`simple` rather than `php` is deliberate. The `php` release-type expects to manage a version key
inside `composer.json`, and Packagist derives the version from the git tag — two sources of truth
for one number, which is the class of problem that produces a package whose declared version and
installable version disagree. Plan 01's manifest test already asserts `composer.json` carries no
`version` key; `simple` is what keeps that true.

01-RESEARCH.md logs this as assumption A4 and recommends verifying against the release-please
config schema before locking it in, since switching release-type later requires a manifest reset.
Verify it, and record the confirmation in the SUMMARY.

Create `.github/workflows/release-please.yml` triggered on push to `main`, with the minimum
permissions release-please needs to open its release pull request.

**It cuts the tag and the GitHub release. It does not publish.** D-28 is explicit that the
GitHub-to-Packagist integration is what turns a tag into an installable version, and D-47 makes
that integration owner-gated and impossible while the repository is private. Do not add a publish
step, a Packagist API call, or a webhook. Record in `docs/repo/owner-gated-checklist.md` (task 3)
that without the integration, tags land and Packagist never notices — the package looks abandoned
while `main` is green. That is the failure mode worth writing down.

Note in the SUMMARY that release-please derives the version bump from individual commits on `main`,
which is why D-25's merge-commit strategy makes commitlint mandatory rather than merely nice: a
stray `feat:` buried inside a branch bumps the minor version.
  </action>
  <verify>
    <automated>node -e "const c=require('./release-please-config.json'); const t=JSON.stringify(c); if(!t.includes('simple')) process.exit(1)" && test -f .release-please-manifest.json && test -f version.txt</automated>
    <automated>! grep -riE 'packagist' .github/workflows/release-please.yml</automated>

<task type="auto">
  <name>Task 2: Supply-chain audit and a backward-compatibility check that works on a greenfield</name>
  <files>.github/workflows/supply-chain.yml</files>
  <read_first>STANDARDS.md §8, §12c; .planning/phases/01-foundation-gates/01-RESEARCH.md "Pitfall 3: roave/backward-compatibility-check's PHP floor keeps rising" and Open Question 2</read_first>
  <precondition>The repository carries no git tag yet, so the backward-compatibility check has no previous release to compare against — verify with `git tag -l` before choosing the guard.</precondition>
  <action>
Create `.github/workflows/supply-chain.yml` with `permissions: contents: read`, on `pull_request`,
with two named jobs.

The `composer audit` job runs on a single PHP version and fails the build on any advisory (D-31).
No `continue-on-error`, no advisory ignore-list. STANDARDS §12c is unambiguous that it fails the
build.

The backward-compatibility job runs `roave/backward-compatibility-check` as a **single
non-matrixed job on PHP 8.4**. This settles 01-RESEARCH.md Open Question 2, and the answer got
easier than that document expected: it agonised over pinning a roave release that still supported
PHP 8.2, and STANDARDS §1's floor raise to `^8.3` removed the constraint entirely. The check
compares source trees, not runtime behaviour, so it does not need to run per PHP version. Run the
current release on PHP 8.4 and do not pin to 8.14.0 as that document suggests.

Then handle the greenfield case honestly. There is no previous tag to compare against, so the tool
has no baseline. Guard the run on `git tag -l` being non-empty and, when it is empty, emit an
explicit message saying the check was skipped because no released version exists yet, and exit
successfully.

The distinction that matters: guard on **the absence of a tag**, not on the tool's exit code. A
`|| true` or a `continue-on-error: true` would pass forever, including after the first release,
which is precisely when the check starts mattering — and "no gate disabled temporarily" is a
cross-phase invariant. Make the skip message loud enough that a human reading a green run
understands the check did not actually compare anything yet.

D-17 also allows a detected break when the PR is labelled `breaking` and targets the next major.
Wire that label check now if it is cheap, or record it in the SUMMARY as Phase 9 work if it is not
— but do not silently drop it.
  </action>
  <verify>
    <automated>composer audit</automated>
    <automated>grep -q 'git tag' .github/workflows/supply-chain.yml && ! grep -qE 'continue-on-error|\|\| true' .github/workflows/supply-chain.yml</automated>
  </verify>
  <done>`composer audit` runs as a named required check with no escape hatch; the BC check runs once on PHP 8.4 and skips-with-a-message only when no git tag exists, guarded on tag absence rather than on exit code.</done>
</task>

Create `docs/repo/owner-gated-checklist.md` with three sections.

**Branch protection.** The exact required-checks list, naming every job across `ci.yml`,
`governance.yml`, `js.yml`, `arch.yml`, `quality.yml`, `docs.yml` and `supply-chain.yml`. Cover
everything D-29 and STANDARDS §12b enumerate: the full tests matrix, Pint, PHPStan, mutation,

`composer validate --strict` — plus the code-shape, source-hygiene and firing-harness jobs this
phase added. Also record the settings that are not checks: PR required, no direct pushes, no
force-push, and merge commits rather than squash (D-25 — squash-merging would delete the RED-to-GREEN

rules may be limited by plan on a private repository.

**Packagist and publishing.** REL-02, Phase 9. Record that release-please cuts tags but does not
publish, and that without the GitHub-to-Packagist integration tags land and Packagist never notices.

**Pages deploy.** Point at `docs/repo/docs-site-deploy.md` from plan 06 rather than restating it.

Then write the FOUND-03 probe.

`docs/probes/association-inverse-probe.md` states the question, the procedure from design spec
§6.4, and a results table to fill in — and states plainly that the answer must come from running
it. `scripts/probes/association-inverse-probe.sh` implements the procedure: read a HubSpot
developer-account token from an environment variable, create a labelled `deals -> contacts`
association, then read `getPage('contacts', $contactId, 'deals')` and record whether it returns
and with which typeId.

Write the script against the HubSpot v4 associations REST endpoints with `curl`, not against
`hubspot/api-client`. Two reasons: the `Gateway` layer does not exist until Phase 2, and R1 confines
`HubSpot\*` to that layer — a probe script reaching for the SDK now would either violate the
boundary or force an exception to it on day one.

**Do not run it, do not fabricate a result, and do not reason to an answer.** HubSpot's
documentation does not state whether creating an association from A to B makes it readable from B
to A; the design spec defines this as an empirical probe precisely because of that. Leave the
results table empty with the date field blank. The consequence of guessing is concrete: if the
inverse is not automatic, `inverse_type_id` becomes write-critical in Phase 3, and a wrong default
writes associations in the wrong direction where nobody notices for months.

Add a safety line the operator will actually read: a **developer test account only, never a
production portal** — the procedure writes real association records.

Record in the SUMMARY that FOUND-03 remains open and is unblocked by exactly one thing: the token.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Packagist advisory database -> repository | `composer audit` is the package's only automated notice of a vulnerable dependency |
| Tagged release -> consumer application | A backward-compatibility break reaches every consumer that resolves the new version |
| Probe script -> HubSpot portal | The probe writes real association records with a real token |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Tampering | vulnerable transitive dependency in a tagged release | high | mitigate | `composer audit` as a required check failing the build on any advisory, plus weekly Dependabot from plan 02 (D-31) |
| T-07-02 | Tampering | a gate built but never made required | high | mitigate | `tests/Ci/RequiredChecksTest.php` fails when the workflow job set and the required-checks list disagree in either direction. Branch protection itself remains owner action and is recorded as such |
| T-07-03 | Information Disclosure | probe token handling | high | mitigate | The probe reads the token from an environment variable, never a committed file, and the results document has no field for it. The script is explicitly scoped to a developer test account |
| T-07-04 | Repudiation | release-please dropping unparseable commits | medium | mitigate | commitlint on every commit (plan 02, D-25) is the precondition. A commit release-please cannot parse is silently absent from the changelog, so the changelog would understate what shipped |
| T-07-05 | Denial of Service | BC check passing vacuously after the first release | high | mitigate | The greenfield skip is guarded on `git tag -l` being empty, not on the tool's exit code, so the check becomes live automatically at the first tag rather than staying permanently green |
| T-07-SC | Tampering | composer installs | high | mitigate | No new packages are installed by this plan. `roave/backward-compatibility-check` was audited OK in 01-RESEARCH.md's Package Legitimacy Audit and enters the tree in plan 01 |
